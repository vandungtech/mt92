## Compatibility result

Let `B` be a v0.3.2 manifest body, including its `source`, and let `H` be the
canonical SHA-256 operation. The signed v0.3.2 miner commits the legacy digest
`L = H(B)`. d77 introduces a content digest `C = H(B without source)` and checks
it first. It then checks `L` as an explicit legacy fallback. That fallback
accepts only when the commitment source equals the manifest source.

Therefore an old v0.3.2 manifest/commitment is forward-compatible with d77
validator semantics, but only with its original equal commitment and manifest
source. The focused static contract test models these branches using an inert
ASCII fixture and also proves that a relocated commitment source is rejected
for the legacy digest.

Compatibility is deliberately one-way. A new d77 miner commits `C`, while an
old v0.3.2 validator computes only `L` and requires source equality. Because
`C` omits `source` and `L` includes it, an old validator does not accept a new
d77-style manifest digest (absent a cryptographic collision). New-manifest to
old-validator operation is unsupported.
